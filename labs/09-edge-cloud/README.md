# W9 小組實作 警報事件與照片上雲

本週延續W7的溫溼度警報與W8的相機，每組在課堂共同完成一套作品，再請助教現場查核。

**本週不繳交報告、截圖、測試輸出或查核表。** 程式留在小組自己的工作repo繼續使用；助教在班級名單記錄結果。W6的個人作業方式不套用到本週。

## 小組如何分工

每組指定一位成員的既有Learner Lab與Codespace作為本組雲端環境，沿用其W6成果；帳號持有人操作部署。其他組員分工處理裝置、雲端串接、操作測試與說明，彼此不交換AWS登入憑證。

本機筆電負責ESP32的USB、燒錄與配網；Codespace負責雲端程式與查詢。雲端Codespace不會直接取得本機USB埠。每組用自己的裝置名稱、client ID與topic，不照抄別組或教師的資源值。

## 開始前先確認

1. W8相機能取得當下照片；感測器與警報條件可用。
2. 筆電與ESP32的STA連線正常，板子可到Internet。
3. 本組W6事件服務／consumer及資料庫可用，consumer允許本次真實裝置ID。
4. 教師／助教已確認本組照片API、私有S3、HTTPS入口與身分配置可用。此基礎服務接在既有平台上，不要求本節課重新建整套AWS架構。
5. 板子完成校時，已配置專用IoT身分、API信任CA與device權杖；operator權杖留在操作端。

未就緒時先請助教定位；修復環境的等待不算作品完成。硬體待修可先做事件或照片的分段練習，現場完整查核待硬體恢復再補。

本機若沿用Arduino CLI，可在已安裝Core 3.3.7的Windows筆電使用提供的工具；程式仍是本組自己的W9 sketch：

```powershell
./tools/w09_build.ps1 -Action ports
./tools/w09_build.ps1 -Action compile -SketchPath ./arduino/W09_CloudCamera
./tools/w09_build.ps1 -Action upload -SketchPath ./arduino/W09_CloudCamera -Port <目前COM埠>
```

若本組已有可用Arduino IDE流程，可沿用；不要在Codespace執行本機USB燒錄。工具預設板型為本課ESP32-S3、16MB Flash／OPI PSRAM／native USB，其他硬體先與助教確認。

## 本週要自己完成的程式

以本組W8程式與W6雲端成果為基礎，由小組完成以下功能。底層相機驅動、TLS函式庫與照片基礎服務依課程提供的介面使用，不重新撰寫。

- 正常轉警報時固定一次事件：裝置、事件ID、發生時間、感測值、門檻與當次原圖；持續警報不再新增。
- 事件以MQTT over TLS送入IoT Core，由既有consumer／API入庫。收到PUBACK後，再以本裝置的HTTPS收據確認事件已存、內容相符。
- 確認事件已存後，以同一event_id經HTTPS上傳當次JPEG；照片存在私有S3，資料庫保留照片與事件的關聯。
- 分開顯示事件與照片進度。當次沒有照片時顯示原因；重試保留原內容，滿載不覆寫仍待處理的照片。

事件本文沿用四個必填欄位：event_id、device_id、observed_at（含時區）、type，可選note。感測值與門檻先放note；未知欄位不直接加入。真實警報用anomaly，測試輸入用test並保留來源標示。

## T1 固定當次事件

把感測值調到正常，再改變門檻或環境使它進入警報。保留前後狀態，僅在NORMAL→ALARM時建立一次事件；SENSOR_ERROR獨立處理。

事件ID包含裝置、當次開機識別與序號；每次新事件使用新ID，重送沿用原ID。網路校時完成後才固定日曆時間。照片須是該次觸發取得的原圖，不在上傳失敗時重新拍另一張冒充。

## T2 確認事件真的存到雲端

由小組把固定事件送到本組topic，觀察發布結果，再查本裝置收據。收據需有相同event_id、正確device_id、event_stored=true，並與原事件內容相符。

PUBACK確認的是MQTT發布階段；後端保存另由收據確認。事件尚在處理時保留原ID有限等待，不用固定delay猜成功，也不改ID掩蓋失敗。

## T3 附上照片，再讓授權者讀回

確認事件入庫後，上傳原JPEG到 `/w09/device/events/{event_id}/photo`。操作端用operator角色從 `/w09/events/{event_id}/photo` 讀回照片，查看內容是否就是當次場景。

可選用教師提供的 [只讀檢查工具](../../tools/w09_check_README.md)，於Codespace執行：

```bash
python3 -m pip install -r tools/requirements-w09.txt
mkdir -p .local
cp labs/09-edge-cloud/config.example.json .local/w09-check.json
# 編輯本組HTTPS入口、device_id與CA檔路徑後：
python3 tools/w09_check.py --config .local/w09-check.json --event-id <本次事件ID>
```

工具會以隱藏輸入詢問device／operator權杖，不把權杖放命令列或檔案。它只查事件收據與照片並保存本地預覽，不發事件、不上傳照片、不修改AWS。第三項持續警報仍由助教看現場結果。

## 請助教查核 三項即可

1. **新事件上雲**：助教看一次現場正常轉警報，雲端查到該組本次新event_id、裝置及時間。時間可從板上事件快照／既有事件頁核對，收據介面本身未回傳完整時間。
2. **照片對應當次事件**：開啟同一event_id的授權照片，看得到當時鏡頭前的內容；助教可在觸發前指定擺放物品或手勢。
3. **持續警報不新增**：完成該次上傳後保持ALARM約10–15秒，觸發計數與最新event_id維持；重新整理本組事件頁確認沒有持續新增。不要解除後又觸發，或在觀察期間重開機。

每組準備好後再請助教，查核約2–3分鐘。只看截圖或舊事件不足以確認本次操作；助教在班級名單勾選三項，未完成項目留待課堂補查核，不另要求電子繳交。

## 可以練習 不列本週必查

原內容重送、跨開機識別、錯誤格式／權限、部分失敗與有限重試都可以練習。完整錯誤碼矩陣、503故障注入、壓力測試與斷電補送不列本週三項現場查核，也不要求提交紀錄。

## 卡住時依序查

本地相機／感測 → Wi-Fi → 校時 → IoT連線 → PUBACK → 後端收據 → 照片API → 授權讀回。事件已存但照片失敗就保留原事件與原因；沒有當次原圖需重新做一次新事件，舊事件不假填完成。

若持續警報卻一直增加事件，先檢查是否每輪讀值都呼叫上傳，而不是只在狀態轉換時建立事件。若查到事件但照片404，先看照片是否仍待送及API角色是否正確。
